1 · Boas Práticas

EXISTS vs IN

Use EXISTS quando você só precisa saber se existe algum registro correspondente — o banco para na primeira ocorrência encontrada. IN com subquery pode precisar materializar toda a lista antes de comparar.

❌ Antipadrão — IN com subquery 
SELECT * FROM clientes
WHERE id IN (
  SELECT cliente_id
  FROM pedidos
  WHERE status = 'ativo'
);
✅ Boa prática — EXISTS 
SELECT * FROM clientes c
WHERE EXISTS (
  SELECT 1 FROM pedidos p
  WHERE p.cliente_id = c.id
    AND p.status = 'ativo'
);

CTE — Materializada vs Não Materializada

MATERIALIZED (padrão até PG 11): força execução separada — útil para isolar um plano.
NOT MATERIALIZED (PG 12+): planejador pode otimizar como subquery, aplicando push-down de filtros.

MATERIALIZED — execução separada 
WITH pedidos_ativos AS MATERIALIZED (
  SELECT * FROM pedidos
  WHERE status = 'ativo'
)
SELECT c.nome, COUNT(p.id)
FROM clientes c
JOIN pedidos_ativos p
  ON p.cliente_id = c.id
GROUP BY c.nome;
NOT MATERIALIZED — planejador otimiza 
WITH pedidos_ativos AS NOT MATERIALIZED (
  SELECT * FROM pedidos
  WHERE status = 'ativo'
)
SELECT c.nome, COUNT(p.id)
FROM clientes c
JOIN pedidos_ativos p
  ON p.cliente_id = c.id
GROUP BY c.nome;

JOIN Explícito

Evite a sintaxe de JOIN implícito com vírgula na cláusula FROM. É fácil esquecer a condição e criar um produto cartesiano acidental — que multiplica o número de linhas e não aparece como erro de sintaxe.

❌ Antipadrão — produto cartesiano implícito 
-- Se esquecer o WHERE, retorna
-- pedidos × clientes linhas!
SELECT * FROM pedidos p, clientes c
WHERE p.cliente_id = c.id;
✅ Boa prática — JOIN explícito 
-- Condição declarada junto com
-- a relação — mais legível e seguro
SELECT * FROM pedidos p
JOIN clientes c
  ON p.cliente_id = c.id;
2 · Antipadrões

Antipadrão 1 — SELECT *

❌ Antes — traz todas as colunas 
SELECT * FROM pedidos
WHERE cliente_id = 42;
-- Problema:
-- • carrega colunas desnecessárias
-- • impede Index Only Scan
-- • transfere mais dados pela rede
✅ Depois — colunas específicas 
SELECT id, total,
  status, criado_em
FROM pedidos
WHERE cliente_id = 42;
-- Permite Index Only Scan com
-- índice cobridor

Antipadrão 2 — Função em Coluna do WHERE

❌ Antes — função impede índice 
-- Aplica UPPER() em cada linha
WHERE UPPER(email) = 'J@EMAIL.COM';

-- Aplica DATE_TRUNC() em cada linha
WHERE DATE_TRUNC('month', criado_em)
  = '2024-01-01';
✅ Depois — função no valor 
-- Normaliza o valor de comparação
WHERE email = LOWER('J@EMAIL.COM');

-- Converte para intervalo
WHERE criado_em >= '2024-01-01'
  AND criado_em < '2024-02-01';
-- Alternativa: índice de expressão
-- CREATE INDEX ON clientes(UPPER(email))

Antipadrão 3 — OFFSET Elevado

❌ Antes — O(n) por página 
-- Na página 5000:
-- lê e descarta 100.000 linhas
SELECT * FROM pedidos
ORDER BY id
OFFSET 100000
LIMIT 20;
-- Fica mais lento a cada página
✅ Depois — keyset: O(1) 
-- Frontend guarda o último id
-- retornado e passa como parâmetro
SELECT * FROM pedidos
WHERE id > :ultimo_id
ORDER BY id
LIMIT 20;
-- Usa índice da PK — sempre rápido

Antipadrão 4 — N+1 Queries

❌ Antipadrão — 1 + N queries 
-- No código da aplicação:
-- SELECT * FROM pedidos → N linhas
-- for each pedido:
--   SELECT * FROM clientes
--   WHERE id = pedido.cliente_id
-- = 1 + N round-trips ao banco
-- Para 1000 pedidos: 1001 queries!
✅ Depois — 1 query com JOIN 
-- Traz tudo de uma vez:
SELECT p.id, p.total,
  c.nome, c.email
FROM pedidos p
JOIN clientes c
  ON p.cliente_id = c.id;
-- 1 query, 1 round-trip

Antipadrão 5 — Conversão Implícita de Tipo

❌ Antes — tipo errado 
-- id é INTEGER, mas passamos STRING
-- PostgreSQL faz cast implícito
-- em cada linha da comparação
SELECT * FROM pedidos
WHERE id = '42';

SELECT * FROM pedidos
WHERE cliente_id = '100';
✅ Depois — tipo correto 
-- Use o tipo nativo da coluna
SELECT * FROM pedidos
WHERE id = 42;

SELECT * FROM pedidos
WHERE cliente_id = 100;
-- Sem cast = pode usar índice
3 · Exercício — Reescrever Queries
✏️
Tarefa: Para cada query: (1) identifique o antipadrão, (2) reescreva a query, (3) compare o plano antes e depois com EXPLAIN ANALYZE.

Query 1 — Função em coluna WHERE

Antipadrão: DATE_TRUNC() na coluna impede uso do índice.

-- Versão corrigida:
EXPLAIN ANALYZE
SELECT * FROM pedidos
WHERE criado_em >= '2024-06-01'
  AND criado_em < '2024-07-01';

Query 2 — OFFSET elevado

Antipadrão: OFFSET lê e descarta 5000 linhas.

-- Keyset pagination:
EXPLAIN ANALYZE
SELECT * FROM pedidos
WHERE id > 5000
ORDER BY id LIMIT 10;

Query 3 — IN com subquery

Antipadrão: IN com DISTINCT desnecessário.

-- Versão com EXISTS:
EXPLAIN ANALYZE
SELECT * FROM clientes c
WHERE EXISTS (
  SELECT 1 FROM pedidos p
  WHERE p.cliente_id = c.id
    AND p.status = 'ativo'
);
