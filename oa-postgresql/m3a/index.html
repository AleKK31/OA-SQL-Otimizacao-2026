1 · Tipos de Índice no PostgreSQL

No módulo 2 você viu que o EXPLAIN pode mostrar Seq Scan (leitura completa da tabela, linha por linha) ou Index Scan (navegação pelo índice, muito mais rápida). A diferença pode ser enorme — de segundos para milissegundos em tabelas com milhões de linhas. O que determina qual estratégia o PostgreSQL usa é a existência e o tipo de índice na coluna filtrada. O PostgreSQL suporta 4 tipos principais de índice, cada um otimizado para um cenário diferente. Escolher o tipo errado pode fazer com que o índice nunca seja usado.

B-Tree — Balanced Tree padrão

Caso de uso: igualdade, intervalo, ordenação, prefixo de string

CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
CREATE INDEX idx_pedidos_criado  ON pedidos(criado_em);

-- ✅ Funciona para:
SELECT * FROM pedidos WHERE cliente_id = 42;
SELECT * FROM pedidos WHERE criado_em BETWEEN '2024-01-01' AND '2024-12-31';
SELECT * FROM clientes WHERE nome LIKE 'João%';  -- prefixo
✗ NÃO funciona: LIKE '%João%' (busca no meio da string)

Por que é o padrão? Suporta os operadores mais comuns (=, <, >, BETWEEN, IN) e pode ser usado em ordenações — um único B-Tree frequentemente elimina Sort + Seq Scan.

GIN — Generalized Inverted Index

Caso de uso: JSONB, arrays, full-text search — dados compostos

CREATE INDEX idx_metadata_gin ON produtos USING GIN(metadata);
CREATE INDEX idx_tags_gin     ON artigos  USING GIN(tags);

-- ✅ Funciona para:
SELECT * FROM produtos WHERE metadata @> '{"cor": "azul"}';
SELECT * FROM artigos  WHERE tags @> ARRAY['postgresql'];
✗ NÃO usar para colunas escalares simples (use B-Tree)

Como funciona? O GIN indexa cada elemento individualmente (cada chave do JSON, cada item do array). É maior e mais lento de construir que B-Tree, mas muito mais rápido para buscas em dados compostos.

GiST — Generalized Search Tree

Caso de uso: dados geométricos, ranges, full-text search por proximidade

CREATE INDEX idx_localizacao ON lojas  USING GIST(coordenadas);
CREATE INDEX idx_periodo      ON eventos USING GIST(periodo); -- tsrange

-- ✅ Funciona para:
SELECT * FROM lojas   WHERE coordenadas <-> POINT(0,0) < 10;
SELECT * FROM eventos WHERE periodo @> NOW();
✗ NÃO usar para igualdades simples (B-Tree é mais eficiente)

vs GIN: GiST suporta mais tipos de dados (geometria, ranges, full-text por proximidade/ranking) mas é mais genérico e menos eficiente que GIN para JSON e arrays. Para JSONB com operador @>, prefira GIN — busca mais rápida. Para dados geoespaciais (PostGIS), ranges temporais (tsrange), ou busca por similaridade de texto (pg_trgm), GiST é a escolha certa. Em resumo: "compostos com elementos discretos" → GIN; "geometrias ou intervalos contínuos" → GiST.

BRIN — Block Range INdex

Caso de uso: tabelas muito grandes com dados naturalmente ordenados por inserção

CREATE INDEX idx_logs_data ON logs USING BRIN(criado_em);

-- ✅ Ótimo para: logs, séries temporais inseridas em ordem
-- BRIN armazena apenas min/max por bloco de páginas
-- Muito pequeno — dezenas de KB mesmo para tabelas de TB
✗ NÃO usar se dados forem inseridos fora de ordem cronológica

Por que tão pequeno? BRIN não indexa cada linha, mas cada bloco de páginas — armazena apenas o valor mínimo e máximo do bloco. Se você busca por data e as linhas foram inseridas em ordem de data, o BRIN descarta blocos inteiros sem verificar cada linha. Se os dados não estão em ordem (ex: datas misturadas por importação de fontes diferentes), o min/max de cada bloco se sobrepõe com todos os outros — o BRIN não consegue descartar nenhum bloco e o banco acaba fazendo um Seq Scan de qualquer jeito, sem ganho algum.

2 · Índice Parcial, Composto e Cobridor

Índice Parcial

Indexa apenas um subconjunto de linhas — muito menor e mais rápido que indexar toda a tabela.

-- Indexa apenas as linhas onde status = 'ativo'
CREATE INDEX idx_pedidos_ativo ON pedidos(cliente_id)
WHERE status = 'ativo';

-- Só será usado quando a query incluir: WHERE status = 'ativo'
SELECT * FROM pedidos WHERE cliente_id = 42 AND status = 'ativo';
-- ✅ usa idx_pedidos_ativo

SELECT * FROM pedidos WHERE cliente_id = 42;
-- ✗ não usa (falta a condição WHERE status = 'ativo')
💡
Se apenas 5% das linhas têm status = 'ativo', o índice parcial é 20× menor que um índice completo — menos I/O, menor footprint em RAM.

Índice Composto — Leftmost Prefix Rule

O índice só é usado se a query filtrar pela primeira coluna (ou pelas primeiras, em ordem).

CREATE INDEX idx_pedidos_comp
ON pedidos(status, cliente_id, criado_em);

-- ✅ FUNCIONA (usa o índice):
WHERE status = 'ativo'
WHERE status = 'ativo' AND cliente_id = 42
WHERE status = 'ativo' AND cliente_id = 42 AND criado_em > '2024-01-01'

-- ✗ NÃO usa o índice:
WHERE cliente_id = 42           -- pula 'status' (1ª coluna)
WHERE criado_em > '2024-01-01'  -- pula as duas primeiras
💡
Por que a ordem importa? O B-Tree composto é ordenado lexicograficamente — primeiro pela 1ª coluna, depois pela 2ª dentro de cada valor da 1ª, e assim por diante. Para usar o índice, o PostgreSQL precisa navegar pela árvore a partir da raiz, que está organizada pela 1ª coluna. Se a query não filtra pela 1ª coluna, o banco não consegue identificar em qual subárvore procurar — é como tentar usar um índice de dicionário organizado por sobrenome quando você só sabe o primeiro nome.

Regra prática

Coloque as colunas de igualdade (=) primeiro, depois as de intervalo (>, <, BETWEEN). A coluna mais seletiva (menos repetida) deve vir antes quando há múltiplas igualdades.

Índice Cobridor — Index Only Scan

Quando o índice contém todas as colunas necessárias, o PostgreSQL não precisa acessar a tabela.

-- A query precisa de: id, total, status
-- Criar índice que cobre todas essas colunas:
CREATE INDEX idx_pedidos_cobridor ON pedidos(cliente_id)
INCLUDE (total, status);

-- Agora esta query usa Index Only Scan (não acessa a tabela):
SELECT id, total, status FROM pedidos WHERE cliente_id = 42;

-- EXPLAIN mostrará:
-- Index Only Scan using idx_pedidos_cobridor on pedidos
--   (cost=0.29..0.51 rows=5 width=32)
💡
INCLUDE() adiciona colunas ao índice sem indexá-las — elas ficam armazenadas nas folhas do B-Tree para leitura, mas não criam entradas extras. Isso evita o acesso à tabela (heap) sem inflar o tamanho do índice tanto quanto indexar.

Trade-offs dos Índices

⚠️
Índices têm custo de manutenção: cada INSERT/UPDATE/DELETE precisa atualizar todos os índices da tabela. Use com moderação.

Índices não são gratuitos. Cada índice que você cria precisa ser atualizado a cada INSERT, UPDATE e DELETE na tabela. Em tabelas com alta taxa de escrita, índices desnecessários podem custar mais em manutenção do que ganham em leitura. Use a tabela abaixo como guia de decisão:

SituaçãoRecomendação
Tabela com muitos INSERTs (ex: logs)Poucos índices, considere BRIN
Coluna com alta cardinalidade e usada em WHEREB-Tree simples
Query com filtro parcial (WHERE status = 'X')Índice parcial
Query precisa de várias colunas do SELECTÍndice cobridor com INCLUDE
Índice nunca usadoRemover! Use pg_stat_user_indexes
 
-- Verificar índices não utilizados:
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
3 · Exercício — Aplicar Índice Correto
💼
Cenário: A query abaixo é executada milhares de vezes por dia e consome 40% da CPU do banco. Analise o plano, identifique o problema e aplique a solução.

Passo 1: Analise o plano ANTES de qualquer otimização

Passo 2: Crie o índice mais adequado e verifique a melhora

-- Solução ótima: índice parcial + cobridor
CREATE INDEX idx_pedidos_ativo_cliente ON pedidos(cliente_id, criado_em DESC)
INCLUDE (total, status)
WHERE status = 'ativo';

-- Por que esse índice?
-- 1. WHERE status = 'ativo' → índice parcial (menor, mais rápido)
-- 2. cliente_id na posição 1 → atende o filtro principal
-- 3. criado_em DESC na posição 2 → atende o ORDER BY sem Sort extra
-- 4. INCLUDE (total, status) → Index Only Scan (não acessa a tabela)
