1 · EXPLAIN e Variantes

O que é o EXPLAIN?

O EXPLAIN é o comando do PostgreSQL que mostra o plano de execução que o planejador escolheu para uma query — sem executá-la de fato. Com ANALYZE, ele executa e mostra os valores reais.
💡
O planejador gera dezenas de planos alternativos e escolhe o de menor custo estimado. O EXPLAIN revela qual foi essa escolha — e por quê pode estar errada.

Variantes do EXPLAIN

ComandoExecuta?O que mostra de extra
EXPLAINNãoPlano estimado, custo estimado
EXPLAIN ANALYZESimTempo real, linhas reais, loops
EXPLAIN (ANALYZE, BUFFERS)Sim+ uso de cache (shared hit/read)
EXPLAIN (ANALYZE, FORMAT JSON)SimSaída em JSON estruturado
⚠️
EXPLAIN ANALYZE executa a query de verdade. Em tabelas de produção, use BEGIN; EXPLAIN ANALYZE ...; ROLLBACK; para evitar efeitos colaterais em operações DML.

Guia de Leitura da Saída

Cada nó na saída do EXPLAIN exibe estes campos — aprenda a ler cada um:

CampoO que significa
cost=0.00..1234.56Custo estimado de iniciar (startup) até terminar (total) — unidade interna arbitrária. O startup é relevante em nós que precisam processar tudo antes de emitir a primeira linha (ex: Sort, Hash).
rows=47Número de linhas estimadas que serão retornadas. Se divergir muito de actual rows, as estatísticas estão desatualizadas — rode ANALYZE.
width=52Tamanho médio de cada linha em bytes. Linhas largas (ex: colunas TEXT grandes) aumentam o uso de memória e o custo de transferência entre nós do plano.
actual time=0.08..198.4Tempo real de iniciar..terminar em ms — só aparece com ANALYZE. Compare com o custo estimado para ver se o planejador acertou a proporção.
loops=1Quantas vezes este nó foi executado. Em Nested Loop Join, o nó interno executa uma vez por linha do nó externo — se o externo retorna 1000 linhas, loops=1000. O custo real é actual time × loops.

Sinal de alerta

Se rows (estimativa) diverge muito de actual rows (real), as estatísticas estão desatualizadas — o planejador está tomando decisões com informações erradas. Solução: ANALYZE tabela;

2 · Plano de Execução e Nós

O que é um Nó de Execução?

Cada operação no plano de execução é um nó. Os nós formam uma árvore — o PostgreSQL executa de baixo para cima (os nós folha primeiro, o nó raiz por último). 
Aggregate  (custo total: 15234.12)
  └── Hash Join  (custo: 12043.00)
        ├── Seq Scan on pedidos    ← executa primeiro
        └── Hash
              └── Seq Scan on clientes  ← executa primeiro

O plano é lido de dentro para fora e de baixo para cima. O nó raiz (Aggregate) só executa depois que todos os filhos terminam.

Tipos de Nó — O que cada um significa

NÓQUANDO OCORRESINAL
Seq Scan Sem índice na coluna filtrada, ou seletividade baixa ⚠️ Tabela grande = problema
Index Scan Índice disponível e seletividade alta ✅ Geralmente bom
Index Only Scan Todas as colunas do SELECT estão no índice ✅✅ Mais eficiente
Bitmap Heap Scan Ocorre com múltiplas condições em índices separados (ex: WHERE status='ativo' AND cidade='SP' com índices independentes). O PostgreSQL monta um bitmap de posições de página e depois acessa a tabela em ordem, reduzindo I/O aleatório. Normal — eficiente para múltiplos índices

Como usar essa tabela na prática

Ao analisar um EXPLAIN: (1) identifique o tipo de scan em cada tabela; (2) verifique se Seq Scan em tabelas grandes tem actual rows muito menor que o total — se sim, falta índice; (3) se rows estimado diverge muito de actual rows, rode ANALYZE na tabela.

Paralelismo no Plano

🔀
Paralelismo: O PostgreSQL pode dividir uma query entre múltiplos workers. Quando isso ocorre, o plano exibe nós com prefixo Parallel: Parallel Seq Scan, Parallel Hash Join, Gather. Controlado por max_parallel_workers_per_gather (padrão: 2).
🧪
No PGLite (modo single-user/WebAssembly): paralelismo não é ativado. Para ver Parallel Seq Scan e Gather, use o Docker com a tabela pedidos (500k linhas).

3 · Estratégias de Join

Três Estratégias de Join

O planejador escolhe automaticamente a estratégia com base no tamanho das tabelas e na disponibilidade de índices. Entender cada uma ajuda a interpretar o plano e criar os índices certos.

EstratégiaComo funcionaQuando o planejador escolhe
Nested Loop Join Para cada linha da tabela externa (outer), varre a tabela interna (inner). Custo: O(n × m). Com índice na coluna de join da tabela interna, o acesso vira O(log m) — muito eficiente. Tabela interna pequena ou com índice na coluna de join
Hash Join Constrói uma hash table em memória com a tabela menor, depois varre a maior comparando cada linha contra o hash. Custo: O(n + m). Requer work_mem suficiente; se o hash não couber, derrama no disco. Tabelas grandes, sem ordenação, sem índice no join
Merge Join Ambas as tabelas precisam estar ordenadas pela coluna de join. O banco avança em paralelo pelas duas sequências mesclando os resultados. Custo: O(n + m) após ordenação — muito eficiente quando os dados já chegam ordenados. Ambas já ordenadas (ex: por PRIMARY KEY ou Index Scan)

Princípio — Quando o Planejador Erra

⚠️ Estatísticas desatualizadas → estratégia de join errada

O planejador escolhe a estratégia automaticamente com base nas estatísticas. Se as estatísticas estiverem desatualizadas, ele pode:

  • Usar Nested Loop em tabelas grandes (achou que eram pequenas)
  • Usar Hash Join onde Nested Loop + índice seria melhor

Sintoma: diferença grande entre rows e actual rows no EXPLAIN ANALYZE.

4 · Ferramentas de Monitoramento

pg_stat_statements e pg_stat_activity

⚠️
Atenção: pg_stat_statements e pg_stat_activity requerem o PostgreSQL completo via Docker. Não funcionam no PGLite.
Execute: psql -h localhost -U oa_user -d oa_db

Essas views são suas ferramentas de diagnóstico de produção — revelam quais queries são mais lentas e o que está rodando agora no banco. Os próximos slides mostram como usá-las.

pg_stat_statements — Top Queries Lentas

Histórico de todas as queries executadas, com tempos acumulados:

-- Top 10 queries mais lentas (por tempo total acumulado)
SELECT
  LEFT(query, 80) AS query_preview,
  calls,
  round(total_exec_time::numeric, 2) AS total_ms,
  round(mean_exec_time::numeric,  2) AS media_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

calls × media_ms = impacto real no banco. Uma query de 200ms chamada 10.000×/dia tem mais impacto que uma de 1s chamada 10×. Use essa view para priorizar o que otimizar primeiro — foque nas queries com maior total_ms. Requer pg_stat_statements habilitado em postgresql.conf (shared_preload_libraries = 'pg_stat_statements').

pg_stat_activity — Queries em Execução Agora

Para diagnóstico em tempo real — use quando o banco está lento agora e você precisa saber o que está rodando:

-- Queries ativas no momento
SELECT pid, usename, state,
  NOW() - query_start AS duracao,
  LEFT(query, 100) AS query
FROM pg_stat_activity
WHERE state = 'active'
  AND pid != pg_backend_pid()
ORDER BY query_start;

-- Forçar encerramento de uma query longa (se necessário):
-- SELECT pg_cancel_backend(pid);

O campo duracao mostra há quanto tempo a query está ativa — queries rodando por minutos geralmente indicam problema (lock, índice ausente, query mal escrita). pg_cancel_backend(pid) cancela suavemente e permite retry; pg_terminate_backend(pid) encerra a conexão completamente.

5 · Exercício — Diagnosticar Query
🔍
Cenário: A tela de pedidos do cliente está demorando mais de 5 segundos. A query abaixo é executada a cada requisição. Identifique o problema e proponha uma solução.

Perguntas para reflexão

  1. Qual é o tipo de nó usado para acessar a tabela pedidos?
  2. As linhas estimadas (rows) batem com as reais (actual rows)?
  3. O que você criaria para melhorar esta query?
-- Problema: Seq Scan em pedidos (sem índice em status e total)

-- Solução 1: índice composto
CREATE INDEX idx_pedidos_status_total ON pedidos(status, total);

-- Solução 2 (melhor): índice parcial para status 'ativo'
CREATE INDEX idx_pedidos_ativo_total ON pedidos(total)
WHERE status = 'ativo';

-- Verificar melhora:
EXPLAIN ANALYZE
SELECT p.id, p.total, p.status, c.nome, c.email
FROM pedidos p
JOIN clientes c ON p.cliente_id = c.id
WHERE p.status = 'ativo'
  AND p.total > 500;
