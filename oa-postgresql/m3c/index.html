Estatísticas, VACUUM e ANALYZE

Docker necessário no exercício
1 · Estatísticas do Planejador

O que são as Estatísticas do Planejador?

O PostgreSQL mantém estatísticas sobre os dados de cada tabela para estimar quantas linhas uma query vai retornar. Essas estatísticas ficam em pg_statistic e são consultadas pelo planejador para escolher o melhor plano.

Os 3 componentes das estatísticas

  • Cardinalidade — quantos valores distintos existem (n_distinct)
  • Histograma — distribuição dos valores em "baldes" (histogram_bounds)
  • MCV — Most Common Values e suas frequências relativas

Cardinalidade — n_distinct e correlation

Ver as estatísticas de uma coluna no Docker:

SELECT attname, n_distinct, correlation
FROM pg_stats
WHERE tablename = 'pedidos'
  AND attname = 'status';

-- n_distinct: número de valores distintos
--   positivo = valor absoluto (ex: 3 para status)
--   negativo = fração das linhas (ex: -0.5 = 50% distintos)
-- correlation: quão ordenados os dados estão fisicamente
--   1.0 = ordem perfeita (ótimo para BRIN)
--  -1.0 = ordem invertida
--   0.0 = aleatório

Histograma e MCV

-- Histograma: distribuição dos valores numéricos
SELECT histogram_bounds
FROM pg_stats
WHERE tablename = 'pedidos' AND attname = 'total';
-- Ex: {10.5, 215.2, 412.8, 601.1, 800.4, 998.9}

-- MCV: valores mais frequentes e suas frequências
SELECT most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'pedidos' AND attname = 'status';
-- Ex: most_common_vals  = {ativo, pendente, cancelado}
--     most_common_freqs = {0.65, 0.25, 0.10}

O planejador usa o MCV para estimar quantas linhas retornam com WHERE status = 'ativo': 65% × total_linhas. Se essa frequência estiver errada (estatísticas antigas), a estimativa erra e o plano pode ser ruim.

Quando as Estatísticas Envelhecem

Se você inserir 100.000 linhas e não rodar ANALYZE, o planejador ainda usa as estatísticas antigas. Ele pode estimar "3 linhas" quando na verdade existem 100.000 — e escolher Nested Loop onde deveria usar Hash Join.

🔴 Princípio: Estatísticas desatualizadas = planos errados

O planejador só é tão bom quanto as estatísticas que tem. Se a tabela mudou muito desde o último ANALYZE:

  • Pode escolher Nested Loop onde deveria usar Hash Join
  • Pode escolher Seq Scan onde um Index Scan seria mais rápido
  • Pode escolher Hash Join onde Nested Loop + índice seria melhor

Sintoma no EXPLAIN: diferença grande entre rows e actual rows.
Solução: ANALYZE tabela; ou VACUUM ANALYZE tabela;

2 · VACUUM e ANALYZE

Por que existem Tuplas Mortas?

O PostgreSQL usa MVCC (Multi-Version Concurrency Control): quando você deleta ou atualiza uma linha, a versão antiga não é removida imediatamente — ela é marcada como "morta" e fica ocupando espaço até o VACUUM limpá-la.

Por que o MVCC faz isso?

Para garantir que transações antigas ainda possam ler a versão antiga da linha — sem bloqueio. Cada transação vê um "snapshot" consistente do banco, mesmo que outras transações estejam modificando dados ao mesmo tempo.

Quando isso é um problema?

Tabelas com muitas deleções ou atualizações acumulam muitas tuplas mortas. Isso aumenta o tamanho físico da tabela, desacelera as varreduras e polui o cache — mesmo que o número de linhas ativas seja pequeno.

VACUUM — Remover Tuplas Mortas

-- Remove tuplas mortas e libera espaço para reuso
-- (não devolve ao SO — o arquivo cresce mas depois é reutilizado)
VACUUM pedidos;

-- VACUUM FULL: compacta e devolve espaço ao SO
-- ⚠️ BLOQUEIA a tabela durante a execução!
VACUUM FULL pedidos;

-- Verificar tuplas mortas antes do VACUUM:
SELECT relname, n_live_tup, n_dead_tup,
  round(n_dead_tup::numeric /
    NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS pct_mortas,
  last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'pedidos';
⚠️
Prefira VACUUM (sem FULL) em produção — não bloqueia leituras nem escritas. Reserve VACUUM FULL para janelas de manutenção quando o espaço em disco for crítico.

ANALYZE — Atualizar Estatísticas

-- Atualiza as estatísticas do planejador
ANALYZE pedidos;

-- Combinar os dois (mais comum):
VACUUM ANALYZE pedidos;

-- Ver quando foi o último ANALYZE:
SELECT relname, last_analyze, last_autoanalyze,
  n_tup_ins, n_tup_upd, n_tup_del
FROM pg_stat_user_tables
WHERE relname = 'pedidos';

Custo do ANALYZE

O ANALYZE faz uma amostragem (por padrão 300 páginas por coluna, controlado por default_statistics_target). É rápido e não bloqueia — pode ser rodado em produção a qualquer momento.

Autovacuum — Manutenção Automática

🤖
Autovacuum: daemon do PostgreSQL que roda VACUUM e ANALYZE automaticamente quando uma tabela acumula muitas tuplas mortas ou modificações. Ativo por padrão. Monitorado por pg_stat_user_tables.last_autovacuum.

Quando o autovacuum não é suficiente

  • Tabelas com carga muito alta de deleções/atualizações
  • Quando autovacuum_enabled = false foi configurado manualmente (como em pedidos_arquivo)
  • Durante migrações de dados de grande volume

Nesses casos, rode VACUUM ANALYZE tabela; manualmente após a operação.

3 · Exercício — Impacto das Estatísticas
🐳
Este exercício requer o Docker. cd docker/ && docker compose up -d — aguarde ~2 min para o seed completar.
1
Verificar o estado inicial da tabela pedidos_arquivo
SELECT relname, n_live_tup, n_dead_tup, last_analyze
FROM pg_stat_user_tables
WHERE relname = 'pedidos_arquivo';
2
EXPLAIN ANALYZE ANTES — observe rows estimado vs actual rows
EXPLAIN ANALYZE
SELECT COUNT(*) FROM pedidos_arquivo WHERE status = 'ativo';
3
Rodar ANALYZE para atualizar estatísticas
ANALYZE pedidos_arquivo;
4
EXPLAIN ANALYZE DEPOIS — compare as estimativas
EXPLAIN ANALYZE
SELECT COUNT(*) FROM pedidos_arquivo WHERE status = 'ativo';
5
Verificar tuplas mortas e rodar VACUUM
SELECT n_dead_tup FROM pg_stat_user_tables WHERE relname = 'pedidos_arquivo';
VACUUM pedidos_arquivo;
SELECT n_dead_tup FROM pg_stat_user_tables WHERE relname = 'pedidos_arquivo';
-- n_dead_tup deve ser 0 ou próximo de 0
